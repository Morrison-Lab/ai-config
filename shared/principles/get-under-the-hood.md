# Get under the hood: inspect implementation details and raw artifacts

When trying to understand what a process is doing,
diagnose an unexpected failure,
or determine the behavior of a tool, library, or harness,
find and inspect the actual source code,
raw logs,
job output,
and live execution paths.
Do not treat systems, abstractions, or tools as opaque black boxes.

## Why black-box reasoning fails

Abstractions, interfaces, and wrappers exist to simplify daily usage,
but they frequently obscure execution mechanics during debugging,
optimization, and verification.
Treating an unfamiliar component as an opaque black box leads to predictable
failure modes:

- **Misleading surface errors**:
  High-level error messages, exit codes, and wrapper exceptions frequently
  compress, truncate, or mischaracterize the underlying failure.
  Relying solely on top-level summaries often sends diagnosis down false paths.
- **Speculative hypothesis loops**:
  Attempting to diagnose behavior from the outside without checking the source
  code or execution logs generates speculative hypotheses that burn time and
  tokens without producing ground truth.
- **Stale or idealized documentation**:
  Documentation and API specs describe intended behavior,
  which may drift from actual implementation details,
  default configurations,
  or edge-case handling in the installed version.
- **Hidden side effects and implicit state**:
  Tools and test harnesses often inject implicit environment variables,
  temporary directories,
  wrapper shims,
  or default arguments that only become visible when reading the underlying
  scripts and configuration manifests.

Software is deterministic and inspectable.
Stepping into the implementation replaces probabilistic guesswork with verified
facts.

## Three operational practices

### 1. Inspect source code directly

Whenever a function, command, action, or tool behaves unexpectedly or requires
precise coordination:

- **Locate the definition**:
  Use codebase search tools (such as Grep, Glob, ripgrep, or search tools)
  or package inspection mechanisms to find the exact file and line where the logic
  is implemented.
- **Inspect the plumbing**:
  Read through the entry points,
  helper functions,
  argument parsers,
  and branch conditions rather than guessing how parameters are interpreted.
- **Trace composite actions and harnesses**:
  For GitHub Actions or CI workflows,
  read the action definition in `actions/` or upstream reusable workflow
  repositories (such as `Morrison-Lab/gha`)
  to see the exact shell commands executed.
- **Inspect dependencies**:
  When a third-party library or package behaves ambiguously,
  inspect the installed source in the environment
  or browse the authoritative upstream repository.

### 2. Inspect raw output and un-truncated logs

When a job, command, test, or process fails:

- **Locate the raw log artifact**:
  Do not stop at a summarized harness message such as "Process failed with exit code 1".
  Find the full stdout, stderr, build log, or joblog generated by the process.
- **Check un-truncated session transcripts**:
  When investigating prior agent sessions or subagent runs,
  examine the raw on-disk conversation logs or session transcript files
  (such as raw JSONL session logs)
  if the interactive view truncated critical command output.
- **Look for early failure indicators**:
  Errors reported at the end of a log are frequently downstream cascades from
  warnings or initial errors emitted earlier in the stream.
  Inspect the full chronological log from the start of the execution step.

### 3. Trace live execution paths and environment state

When static source reading is insufficient to resolve runtime behavior:

- **Check the active environment**:
  Inspect environment variables,
  working directories,
  active shell options (`set -e`, `set -u`),
  and PATH configurations.
- **Enable verbose and debug output**:
  Re-run reproducible commands with debug flags enabled
  (e.g., `--verbose`, `DEBUG=1`, `set -x` in shell scripts,
  or harness-specific log level overrides).
- **Inspect intermediate artifacts**:
  Check temporary files,
  generated cache files,
  staged files,
  and process exit statuses directly rather than inferring them from subsequent
  steps.

## A guard's refusal message goes unread precisely because it arrives with a remedy

The failure modes above all concern a component you are trying to *use*.
A blocking hook is the case where the component is trying to stop you,
and it is the one where black-box reasoning survives longest ---
not because the message is uninformative,
but because it arrives already shaped like an answer.
A refusal that ends in an imperative reads as a prompt to act rather than as a specification to study,
so the eye takes the verb and skips the qualifiers.
The qualifier was in the message on both occasions this was measured,
and was read past on both.

The economics are lopsided and easy to get backwards.
Reading the hook source costs a couple of minutes and is bounded.
Re-attempting the blocked command costs a full cycle each time,
produces the identical message,
and cannot distinguish "my attempt was malformed" from "the guard is broken" ---
so a run of failures reads as evidence of a bug in the guard rather than as evidence you have not read it.

Two measured shapes, from 2026-09-02 and the small hours of 2026-09-03 Pacific:

- **The remedy sentence names the simplest discharge and gets read as scenery.**
  [`no-push-without-self-review.py`](../../hooks/no-push-without-self-review.py)'s refusal says to dispatch `adversarial-reviewer` **in the foreground**.
  On 2026-09-02 that sentence was read six times across four blocked pushes and registered as boilerplate;
  six reviews were dispatched with `run_in_background: true`,
  none of the six produced a verdict the push could consume,
  and the loop was misdiagnosed as a stale-fingerprint bug until a foreground dispatch cleared it on the first try.
  Read the failure as evidence about those six dispatches rather than about the mode:
  the hook does credit a background dispatch whose task notification lands and whose task id matches,
  per [`mistake-patterns.md`](../../memories/mistake-patterns.md) Pattern 43 and the `is_task_notification` branch #2820 added.
  What the message offered was the path with the fewest ways to go wrong,
  and skipping to the command example is what cost four cycles.
- **The remedy sentence carries a structural condition that reads as an aside.**
  [`no-unreviewed-pr.py`](../../hooks/no-unreviewed-pr.py) credits a reviewer request only when it is the **last simple command** in the Bash call,
  because otherwise the call's exit status belongs to some later command.
  Six attempts were made and five failed on that condition alone ---
  three piped to `head`, two with a trailing `; echo "EXIT=$?"` ---
  while every request had genuinely succeeded.
  The sixth, a bare single-command request with nothing chained after it,
  was the only one credited.
  Its refusal text states the condition outright --- "Request it now,
  as the only command in this call" --- and has since `462de02b3`,
  committed 2026-09-02 at 23:41 PDT, under an hour before these attempts.
  The clause was skipped five times in favour of the command example printed below it.

**Diagnosing a guard and changing the habit are separate acts**,
which is the sharper half and the one no amount of reading prevents.
In the second case above the mechanism was read,
stated correctly in the session's own reply,
and then violated on the very next call ---
the next request went out piped to `head` again.
Understanding arrives as a sentence;
compliance has to arrive as a different keystroke.
So after diagnosing a guard,
write the corrected invocation out in full and use that literal string,
rather than trusting that knowing the rule will change what you type.

- **Do:** read the refusal's remedy clause word by word,
  including every qualifier, before composing the second attempt ---
  the prose around the command example is where the condition lives.
- **Do:** open the hook's source the first time the message does not resolve it,
  which costs minutes and is bounded, rather than re-attempting,
  which costs a cycle per try and returns the identical text.
- **Do:** write out the exact corrected command after diagnosing a guard,
  and reuse that string.
- **Don't:** treat a repeated identical refusal as evidence the guard is malfunctioning;
  it is far likelier evidence the message has not been read to the end.
- **Don't:** skip from a refusal's verb to its command example ---
  the qualifier between them is what the guard actually parses.
- **Don't:** read having explained the mechanism as having adopted it.

## In review

Apply this principle during code review and adversarial self-review:

- **Flag speculative remedies**:
  When a diff purports to fix a bug or unexpected behavior,
  verify whether the PR description or commit message references the concrete
  root cause identified in source or logs,
  or whether it applies a speculative workaround to surface symptoms.
- **Flag unnecessary black-box wrappers**:
  Reject changes that add layers of abstraction or error-swallowing wrappers
  simply to mask unexplained tool or harness behavior.
- **Ensure verifiable diagnostics**:
  Ensure that diagnostic tools, error messages, and scripts expose sufficient raw
  detail (such as actual command strings, exit codes, and paths)
  so future failures can be diagnosed under the hood.

## Relation to other principles

- **Serves valid and reproducible development**:
  Grounded verification prevents building on flawed assumptions about how
  dependencies or platform tools operate.
- **Complements Fail Fast** ([`fail-fast`](fail-fast.md)):
  Fail-fast ensures that errors surface loudly and immediately;
  getting under the hood ensures that once an error surfaces,
  diagnosis inspects the exact failure site rather than guessing at symptoms.
- **Complements Deterministic Tools** ([`deterministic-tools`](deterministic-tools.md)):
  Deterministic tools provide inspectable, reproducible mechanisms;
  getting under the hood is the diagnostic practice of actually inspecting
  those mechanisms when understanding or troubleshooting them.
- **Supports Diagnostic Mandate** ([`AGENTS.md`](../../AGENTS.md)):
  Diagnostic requests mandate inspecting live state and raw outputs to deliver
  concrete fixes rather than speculative explanations.
